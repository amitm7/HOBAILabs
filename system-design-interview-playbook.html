1. The Universal Framework

Every system design interview — regardless of the system type — rewards the same disciplined sequence. For a 45-minute interview, budget your time like this:

1

Clarify Requirements — 5 to 8 min

Functional: What exactly must the system do? Pick the 2–3 core features and explicitly de-scope the rest ("I'll focus on posting and reading the feed; I'll skip DMs unless you want them").
Non-functional: Scale (users, QPS, data size), latency targets, availability vs consistency priority, read/write ratio, data retention, geography.
Ask, don't assume. The single most common failure is designing the wrong system. Write requirements down — you'll trace every later decision back to them.

2

Back-of-Envelope Estimation — 3 to 5 min

Compute QPS (average and peak ≈ 2–5× average), storage growth per year, and bandwidth. The goal is not precision — it is deciding which class of design you need: one Postgres box vs a sharded fleet; one worker vs a Spark cluster. State the conclusion out loud: "≈10K writes/sec means a single DB won't hold — we'll need partitioning."

3

API / Interface Design — 3 to 5 min

Define the system's contract: REST/gRPC endpoints for online systems, input/output datasets and schedules for batch, event schemas and topics for streaming. Include request/response shapes, pagination, idempotency keys for writes.

4

High-Level Design — 10 to 15 min

Draw the boxes-and-arrows end-to-end path first: client → LB → services → cache → storage (or source → ingest → process → sink). Walk through the primary read path and the primary write path explicitly. Get interviewer buy-in before going deep: "Does this look reasonable? Where would you like me to zoom in?"

5

Deep Dives — 10 to 15 min

Pick the 2–3 hardest sub-problems (or the ones the interviewer nudges toward): data model & partitioning, the cache strategy, the fan-out choice, exactly-once semantics, the hot-key problem. This is where senior signal lives — trade-offs, not features.

6

Wrap-Up: Bottlenecks, Failures, Evolution — 3 to 5 min

Proactively name single points of failure, what happens at 10× scale, monitoring/alerting, and what you'd build differently with more time. Ending with self-critique is a strong senior signal.

The golden rule: every design choice must be justified by a requirement or a number. "I'll use Cassandra" is worthless; "we have 50K writes/sec, simple key access, and no cross-row transactions, so a leaderless wide-column store like Cassandra fits better than Postgres" is the whole game. Always give the alternative you rejected and why.

4.1 Cross-cutting techniques to name-drop with substance

  • Replication: leader-follower (simple, read scaling, failover lag), multi-leader (multi-region writes, conflict resolution needed), leaderless/quorum (Dynamo-style, R+W>N).
  • Partitioning/Sharding: hash (uniform, no range scans) vs range (scans, hot spots) vs consistent hashing (smooth resharding). Always discuss the hot-key/celebrity problem and resharding story.
  • Idempotency: client-generated request IDs + dedupe table; the answer to "what about retries/duplicates?" in all three archetypes.
  • Rate limiting: token bucket at the edge; protects everything downstream.
  • Circuit breakers, timeouts, retries with exponential backoff + jitter: the resilience trio for any service-to-service call.
  • CDC (change data capture): stream DB changes (Debezium) to keep caches, search indexes, warehouses in sync without dual writes — dual writes are a classic trap, call it out.
  • Observability: RED metrics (rate, errors, duration), structured logs, tracing; for pipelines: lag, throughput, watermark delay, DLQ depth.

5. Deep Dive A — Live Online (Request/Response) Systems

Examples: URL shortener, news feed, chat, e-commerce checkout, ride-hailing, rate limiter, notification service.

A.1 The canonical skeleton

Client → DNS/CDN → Load Balancer → API Gateway (auth, rate-limit) → Stateless services → Cache → Database (replicated, then sharded), with a queue → async workers branch for anything that doesn't need to happen in-request (emails, thumbnails, fan-out, analytics events).

A.2 The five questions that always come

  1. How do reads scale? Ladder: add cache (cache-aside is the default; discuss TTL vs explicit invalidation) → add read replicas (mention replication lag and read-your-own-writes) → add CDN for cacheable responses → denormalize/precompute (materialized views, fan-out-on-write feeds).
  2. How do writes scale? Ladder: vertical → queue-buffer the spikes → partition/shard the database (pick the shard key by your dominant query; discuss hot keys) → consider an LSM/NoSQL store built for writes.
  3. Consistency vs availability? Identify which operations need strong consistency (payments, inventory, usernames — use transactions/conditional writes) and which tolerate eventual (feeds, counters, profiles). Most systems are hybrid; saying that is the senior answer. Mention CAP only in one sentence, then talk in terms of user-visible anomalies.
  4. How does it fail? Kill each box in your diagram: LB (redundant pair), service (stateless → just respawn), cache (stampede → jittered TTLs, coalescing; degrade to DB with load shedding), DB leader (failover, possible lag-window data loss), whole region (DNS failover, active-passive vs active-active).
  5. Real-time delivery? Polling (simple, wasteful) → long polling → WebSocket/SSE (persistent connection service, needs sticky routing + a pub/sub backbone like Redis pub/sub or Kafka to route messages across connection servers).

A.3 Classic sub-problems & their standard answers

Sub-problemStandard answer
Unique ID generationSnowflake-style: timestamp + machine ID + sequence (sortable, no coordination); or ticket DB ranges; UUIDs if ordering irrelevant
Feed fan-outFan-out-on-write (push) for normal users; fan-out-on-read (pull) for celebrities; hybrid is the expected answer
Counting likes/views at scaleDon't increment a DB row per event: buffer in Redis / aggregate via stream, flush periodically; accept approximate real-time counts
Inventory / double-bookingConditional write (optimistic concurrency) or short-lived lock/reservation with TTL; never check-then-write without atomicity
Rate limiterToken bucket in Redis (Lua for atomicity); local + global two-tier for scale
Geo queries (find nearby X)Geohash / quadtree index; shard by region; hot-city problem → finer cells
Distributed transactionsAvoid 2PC; use sagas (compensating actions) or outbox pattern + CDC for atomically publishing events with DB writes

A.4 What "good" sounds like here

"The write path is: client posts → API validates → write to Postgres (source of truth) → outbox event → Kafka → workers update Redis feed caches and Elasticsearch. Reads hit Redis first, ~95% hit rate, fallback to DB with request coalescing. p99 read is a single Redis round-trip, ~2 ms in-region. If Redis dies we shed load at the gateway rather than melt the DB."

6. Deep Dive B — Batch Processing Systems

Examples: nightly ETL to a warehouse, search index rebuild, ML feature/training pipeline, billing/invoice run, log analytics, recommendation precompute.

B.1 The canonical skeleton

Sources (OLTP DBs via CDC/dumps, logs, events) → Ingestion/Landing (S3/HDFS, raw zone) → Processing engine (Spark/MapReduce-style, DAG of transforms) → Serving store (warehouse for analysts, KV store for online lookup, index files) — all coordinated by an orchestrator (Airflow/Dagster: schedules, dependencies, retries, backfills).

B.2 The concepts that earn points

  1. Idempotency & reruns are the #1 topic. Jobs fail and get rerun; partial output must never corrupt results. Standard answers: write to a staging location then atomically swap/rename; overwrite partitions (e.g., date=2026-07-06) rather than append; deterministic transforms.
  2. Partitioning of data (usually by date/hour + a second key): enables incremental processing, targeted backfills, and pruning at query time.
  3. Columnar formats (Parquet/ORC) + compression: 10–100× scan savings for analytics; row formats (Avro) for ingestion.
  4. The shuffle is the bottleneck. Wide dependencies (joins, groupBys) move data across the network. Mitigations: broadcast joins for small tables, pre-partitioning/bucketing on join keys, combiners/partial aggregation, and data-skew handling (salting hot keys) — mentioning skew is a strong signal.
  5. Fault tolerance model: recompute from lineage / retry failed tasks; speculative execution for stragglers; checkpointing for very long DAGs.
  6. Backfill story: how do you reprocess 2 years of data after a logic fix without disturbing the daily runs? (Parameterized jobs by partition, separate backfill queue/cluster, priority isolation.)
  7. Data quality gates: row-count/null/distribution checks between stages; quarantine bad records to a dead-letter location instead of failing the world.
  8. SLA math: "Daily job must finish by 6 am; input is 5 TB; at 200 MB/s/node scan rate, N nodes ≈ …" — sizing the cluster from numbers is exactly the estimation skill they want.

B.3 Classic sub-problems & standard answers

Sub-problemStandard answer
Getting OLTP data out without hurting prodRead replicas for dumps, or CDC (Debezium→Kafka→lake) for continuous, low-impact sync
Late-arriving / corrected source dataReprocess affected partitions; keep raw immutable zone so everything is re-derivable
Small-files problemCompaction jobs; write fewer, larger files (~128 MB–1 GB)
Schema evolutionSchema registry, additive-only changes, versioned datasets
Serving batch output onlineBulk-load into KV store (e.g., build immutable files, hot-swap pointers) — never row-by-row inserts into the serving DB
Orchestration failure semanticsRetries with backoff, alerts on SLA miss, task-level idempotency so retries are safe
Trap to avoid: designing batch as "a big cron + a for-loop". Show the DAG, the partition layout, the rerun/backfill story, and the staging-then-swap output pattern — that's what separates batch answers.

7. Deep Dive C — Live Stream Processing Systems

Examples: real-time metrics/monitoring, fraud detection, trending topics, live leaderboards, ad-click counting, driver location tracking, real-time recommendations.

C.1 The canonical skeleton

Producers → Ingestion log (Kafka/Kinesis: partitioned, replayable, retention window) → Stream processor (Flink / Kafka Streams / Spark Structured Streaming: stateful operators, windows) → Sinks (Redis for live serving, ClickHouse/Druid for real-time analytics, S3 for archive)

The partitioned log is the heart: it decouples producers from consumers, absorbs bursts, allows replay after bugs, and its partition key determines parallelism and ordering (order is guaranteed only within a partition — choose the key so that events that must be ordered share one, e.g., user_id).

C.2 The concepts that earn points

  1. Event time vs processing time. Events arrive late and out of order (mobile clients, retries). Decide which time your results are about. This single distinction drives everything below.
  2. Windows: tumbling (fixed, non-overlapping — per-minute counts), sliding/hopping (overlapping — "last 5 min, every 10 s"), session (gap-based — user activity bursts).
  3. Watermarks: the system's claim "I've probably seen everything up to time T" — the trigger to close windows. Trade-off: tight watermark = fast results, more dropped/late data; loose = slower, more complete. Late events beyond the watermark → side output / correction path.
  4. Delivery semantics: at-most-once (loss ok), at-least-once (duplicates — pair with idempotent sinks; the pragmatic default), exactly-once (checkpointed state + transactional/2-phase sinks, e.g., Flink checkpoints + Kafka transactions — say "effectively-once, within the framework's boundary, at a latency cost").
  5. Stateful processing: counts, joins, sessions need state. Where does it live? Local (RocksDB) per operator, checkpointed to S3; recovery = restore checkpoint + replay log from the checkpoint's offsets. This checkpoint/replay pairing is the streaming fault-tolerance answer.
  6. Backpressure: when a sink slows, the system must slow consumption rather than OOM; the log absorbs the backlog; monitor consumer lag as the #1 health metric. Scale by adding partitions + consumers (up to partition count).
  7. Hot partitions: celebrity key overloads one partition → salt the key (split into K sub-keys, aggregate downstream) or two-stage aggregation (local pre-agg then global).
  8. Serving results: processor writes aggregates to Redis (live counters/leaderboard: sorted sets) or a real-time OLAP store (Druid/Pinot/ClickHouse) for slice-and-dice queries.

C.3 Lambda vs Kappa (say this when asked "what about correctness?")

LambdaKappa
IdeaStream layer for fast approximate results + batch layer recomputes truth from raw data; serving layer mergesOne streaming pipeline; achieve correction by replaying the log with fixed code into a new output, then switch over
ProBattle-tested; batch layer catches all streaming errorsOne codebase, one system; simpler ops
ConTwo codebases computing the same logic — drift and double maintenanceNeeds long log retention and mature exactly-once streaming

C.4 Classic sub-problems & standard answers

Sub-problemStandard answer
Top-K / trending in real timeTwo-stage: per-partition count-min sketch / local top-K → merge globally per window; exact counts don't scale, approximate is expected
Distinct users (cardinality)HyperLogLog (~KBs for millions of distinct, ~2% error) — exact requires huge state
Stream joins (click ↔ impression)Windowed join with state + TTL; discuss what happens when one side is late (buffer bounds, emit-and-correct)
Duplicate events from producersIdempotent producer IDs / dedupe by event-ID within a state TTL window

What "good" sounds like here: "Click events keyed by ad_id into Kafka (say 100 partitions for 100K events/s). Flink consumes with 1-minute tumbling windows on event time, watermark 30 s; late clicks go to a side output that issues corrections. State in RocksDB, checkpoints every 30 s to S3 — on crash we restore and replay from checkpoint offsets, giving effectively-once counts in the Redis sink because writes are keyed upserts (idempotent)."

8. Decision Cheat-Tables

8.1 SQL vs NoSQL (default to SQL; move for a reason)

Choose relational when…Choose NoSQL when…
Transactions/constraints matter (money, inventory, bookings)Write throughput or dataset exceeds a comfortable single-leader setup (>~10K writes/s, >~5–10 TB hot)
Access patterns are evolving / ad-hoc queries & joins neededAccess patterns are few and known → model tables per query
Data is naturally relational and modest scaleNeed multi-region active-active writes or tunable consistency
Middle paths worth naming: read replicas + cache before sharding SQL; NewSQL (Spanner/Cockroach) when you need both scale and transactions.

8.2 Push vs Pull (feeds, notifications, dashboards)

Push (precompute on write)Pull (compute on read)
Fast reads; work ∝ writes × followersCheap writes; work ∝ reads × followees
Bad for celebrities (fan-out explosion)Bad for very active readers / slow reads
Expected answer: hybrid — push for normal users, pull-and-merge for high-fanout accounts.

8.3 Sync vs Async

In-request only what the user must see to proceed; everything else (notifications, indexing, analytics, media processing) goes through a queue. Justify with p99: every synchronous downstream call adds its tail latency to yours.

8.4 Consistency menu (talk anomalies, not acronyms)

LevelUser-visible promiseUse for
Strong / linearizableEveryone sees the latest writeBalances, inventory, unique usernames, locks
Read-your-own-writesYou see your own updates immediatelyProfiles, posts (route author reads to leader / session pinning)
Monotonic readsTime never goes backwards for one userFeeds, timelines (sticky replica per session)
EventualConverges, briefly staleCounters, likes, recommendations, search freshness

8.5 Compute engine quick-pick

NeedReach for
Request/response < 100 msStateless services + cache + OLTP store
Bounded data, minutes–hours OKSpark on object storage, orchestrated DAG
Unbounded, seconds, stateful correctnessFlink (or Kafka Streams for lighter jobs)
Unbounded, sub-minute, simple aggregationsSpark Structured Streaming (micro-batch) is fine — say why it's acceptable
Interactive analytics on fresh eventsReal-time OLAP: ClickHouse / Druid / Pinot

9. How You're Graded + Common Failure Modes

9.1 What interviewers score

  • Problem structuring: did you clarify, scope, and drive the conversation with a plan?
  • Quantitative grounding: did numbers drive decisions (or at least accompany them)?
  • Breadth then depth: a complete end-to-end design first, then genuine depth in 2–3 areas.
  • Trade-off fluency: every choice framed against a rejected alternative with the reason.
  • Failure thinking: unprompted discussion of what breaks and what happens then.
  • Communication: thinking out loud, checking in, adapting to hints. An interviewer's hint is a gift — take it immediately.

9.2 The classic failure modes

FailureAntidote
Jumping to boxes before requirementsForce yourself through steps 1–2; write requirements where both can see them
Buzzword dropping ("we'll use Kafka") without whyNever name a technology without the property that earns it its place
Designing for Google scale when they said 10K users (or vice versa)Let the estimation dictate the ambition; say "at this scale, a single Postgres + replica is honestly enough"
Ignoring the write path / focusing only on readsWalk both paths explicitly in the high-level design
Monologuing 15 minutes without check-insPause after each phase: "shall I go deeper here or move on?"
No failure storyBefore wrap-up, kill every box in your diagram out loud
Treating hints as interruptionsHints = the rubric leaking; pivot immediately and thank them
Perfect-memory trivia focus (exact Kafka configs)Concepts and trade-offs matter; precise numbers only for estimation

10.2 A 2-week practice plan

  1. Days 1–2: internalize the framework (§1) and numbers (§3) until estimation is reflexive.
  2. Days 3–5: one online-archetype question per day (URL shortener → feed → chat), 45 min on a timer, out loud, diagram on paper/whiteboard.
  3. Days 6–7: batch: design an ETL warehouse pipeline and a search-index build; force yourself through the rerun/backfill story.
  4. Days 8–10: stream: ad-click counting, trending topics, metrics system; drill windows/watermarks/exactly-once until you can explain them to a non-engineer.
  5. Days 11–12: hybrids (Uber, YouTube, notifications) — practice saying the classification out loud and switching vocabularies mid-design.
  6. Days 13–14: mock interviews (a friend or record yourself). Grade against §9.1. Fix your single worst habit, not everything.
The one-paragraph summary: Clarify and scope → estimate and let numbers set the ambition → define the interface → draw the end-to-end skeleton for the archetype (serve / DAG / log-process-sink) → go deep on the 2–3 hard parts with explicit trade-offs → kill every box and describe the blast radius → wrap with evolution. Justify everything; volunteer failure modes; treat hints as gold.
